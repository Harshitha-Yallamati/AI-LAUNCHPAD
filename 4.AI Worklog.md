# 4. AI Worklog

## Example 1 — Connecting the incomplete frontend

**Prompt:** Inspect the existing AI Project Launchpad workspace, run it, and identify what remains before completing the connected application.

**AI output:** The review found existing landing, dashboard, registration, local-store, and UI components, but no React entry point/router and no Ambassador, Analytics, Budget, or Settings pages. It proposed retaining the existing Vite/React/Zustand architecture and connecting the missing routes rather than rebuilding the project.

**What I changed or rejected:** I accepted the incremental approach. I added the application entry point, routing, shared admin shell usage, and the four missing operational pages. I rejected a full framework rewrite because the existing component and demo-data structure was already usable.

**Final output:** A working Vite SPA with public registration flow plus Dashboard, Registrations, Ambassadors, Analytics, Budget, and Settings routes. Lint and production build pass.

## Example 2 — Security and feature-gap audit

**Prompt:** Compare the implementation against the Growth Engine requirements and report what actually works, including registration, referrals, analytics, authentication, database security, and deployment.

**AI output:** The audit distinguished UI behavior from production behavior. It found that registration, duplicate prevention, referrals, CSV export, metrics, and scenarios worked only in browser-local Zustand storage. It identified missing server-side authorization, database constraints, RLS, real admin authentication, and tests as critical gaps.

**What I changed or rejected:** I accepted the recommendation not to describe browser-local data as secure production data. I rejected embedding a service-role key or relying on a hardcoded client-side admin password. The demo mode was retained as a clearly separate fallback instead of being removed.

**Final output:** A prioritized issue report, Render deployment Blueprint, ignored environment-file pattern, and a plan to secure public registration through Supabase.

## Example 3 — Supabase registration hardening

**Prompt:** Connect the project to Supabase without exposing secrets and make registration, duplicate prevention, referral validation, and private records production-safe.

**AI output:** The recommended design was a public `register_workshop` RPC protected by database constraints and RLS, plus a separate referral-validation RPC. The browser would use only the Project URL and publishable key; no direct anonymous read access to registrations would be granted.

**What I changed or rejected:** I accepted the RLS/RPC design and added the Supabase client, ignored local environment configuration, and SQL migration. I rejected direct anonymous table inserts/selects and any browser use of a service-role key. After the migration was applied, I verified a synthetic registration, duplicate rejection, invalid-referral rejection, and zero anonymous registration rows.

**Final output:** `supabase/migrations/20261029_initial_growth_engine.sql`, `src/lib/supabase.ts`, and production registration integration when Demo Mode is disabled. The dashboard/admin data views remain intentionally local until Supabase Auth and admin queries are connected.
